# REQUIEM MEMORY CORE MVP

Version: 0.1

Document Type:
Minimum Viable System Definition

Purpose:
Define the first practical implementation stage of the REQUIEM Memory Core system.

---

# 1. MVP PURPOSE

The purpose of the first Memory Core version is:

> Create a reliable project continuity system with minimum complexity.

The MVP must solve the main problem:

Loss of project understanding between:

- development sessions;
- AI conversations;
- project stages;
- future maintenance.

---

# 2. MVP PHILOSOPHY

The first version must not attempt to create full autonomy.

The goal is not:

- replace developer decisions;
- build a complete AI agent;
- create a user-facing product system.

The goal is:

Create a stable memory foundation that can evolve.

---

# 3. MVP CORE FUNCTIONS

The first version consists of five main capabilities:


STATE

↓

DECISIONS

↓

SCANNING

↓

CHECKPOINTS

↓

CONTEXT GENERATION


---

# 4. STATE MANAGEMENT

Purpose:

Maintain the current understanding of the project.

The system must know:

- current phase;
- current objectives;
- completed milestones;
- active tasks;
- blockers.

Example:


Project:

REQUIEM

Phase:

Phase 1

Status:

Architecture preparation

Next:

Core implementation


---

# 5. DECISION MEMORY

Purpose:

Preserve important project reasoning.

The system stores:

- decision;
- reason;
- alternatives;
- consequences;
- status.

Example:


Decision:

REQUIEM remains independent from specific games.

Reason:

Future compatibility.

Status:

Active.


---

# 6. PROJECT SCANNER

Purpose:

Understand the real project state.

The scanner detects:

- new files;
- removed files;
- changed structure;
- dependency changes;
- important modifications.

The scanner does not decide.

It provides information.

---

# 7. CHECKPOINT SYSTEM

Purpose:

Create recovery points.

MVP checkpoints include:

- timestamp;
- project state;
- documentation state;
- change summary.

Example:


CHECKPOINT_001

State:

Documentation foundation complete.

Purpose:

Safe point before implementation.


---

# 8. CONTEXT GENERATION

Purpose:

Create a compact project understanding package.

The system should generate:


REQUIEM_CONTEXT.md


Containing:

- project identity;
- current state;
- important decisions;
- recent events;
- next actions.

Purpose:

Allow a new AI session to understand REQUIEM quickly.

---

# 9. NOT INCLUDED IN MVP

The following are intentionally postponed:

## Full AI automation

Reason:

Requires stable memory structure first.

---

## Automatic documentation rewriting

Reason:

Risk of incorrect historical changes.

---

## REQUIEM integrated administration panel

Reason:

Future ecosystem feature.

---

## Autonomous project decisions

Reason:

AI assists but does not own project direction.

---

# 10. MVP WORKFLOW

Initial workflow:


Project Changes

↓

Scanner detects changes

↓

State report created

↓

Human reviews importance

↓

Memory updated

↓

Checkpoint created if required

↓

Context package regenerated


---

# 11. SUCCESS CRITERIA

MVP is successful when:

A new AI session can understand REQUIEM without previous chat history.

The developer can identify:

- current position;
- important decisions;
- previous milestones;
- next actions.

Project recovery is possible after mistakes.

---

# 12. FUTURE EVOLUTION

After MVP validation:

Possible additions:

- Gemini analysis;
- GPT validation;
- automatic classification;
- advanced backup;
- visual administration;
- REQUIEM ecosystem integration.

---

# 13. FINAL PRINCIPLE

The first Memory Core version does not need to be powerful.

It needs to be reliable.

A small reliable memory system is more valuable than a large uncontrolled automation system.

---

END OF MVP DEFINITION
