# REQUIEM ARCHITECTURE MAP MODEL

Version: 0.1

Status: DRAFT


---

## 1. Purpose


Architecture Map Model defines how REQUIEM represents structured knowledge about project architecture.


The purpose of the Architecture Map:

- describe project systems;
- describe relationships between components;
- preserve architectural understanding;
- provide context for Analysis Layer;
- support future multi-project knowledge.



Architecture Map is not a file explorer.

Architecture Map is not a copy of project structure.

Architecture Map represents understanding of the project.



---

## 2. Position inside Memory Core


Architecture Map belongs to the knowledge layer of Memory Core.


The relationship:


Project

↓

Project Data

↓

Observation

↓

Analysis

↓

Architecture Knowledge

↓

Architecture Map

↓

Memory Core



The map does not replace snapshots, comparison or change records.


It provides additional meaning for detected changes.



---

## 3. Architecture Map principles


### 3.1 Project independence


Architecture Maps belong to projects.


Example:


REQUIEM

|

├── Project A

│   └── Architecture Map

|

├── Project B

│   └── Architecture Map



Memory Core remains independent from any single project.



---

### 3.2 Human authority


Architecture knowledge represents understanding of the project.


Because of this:

- humans approve architecture knowledge;
- automatic systems may suggest changes;
- Memory Core does not silently rewrite architecture.



AI may prepare drafts.

Human approval creates trusted knowledge.



---

### 3.3 Separation from file structure


Files are implementation details.


Architecture describes meaning.


Example:


File:



Scripts/Quest/main.lua



Architecture knowledge:



System:
Quest System

Component:
Quest Logic

Role:
Controls quest progression




The same architecture concept may contain multiple files.

## 5. Architecture entities


Architecture Map may contain:


### Project


The complete project represented by Memory Core.



### System


A major functional area.


Examples:

- Rendering;
- AI;
- UI;
- Quests;
- Audio.



### Subsystem


A smaller part of a system.



### Component


A specific implementation unit.


Examples:

- module;
- service;
- configuration group.



### Resource


A concrete project element.


Examples:

- files;
- assets;
- configuration data.



### Decision


A documented architectural choice.



---

## 6. Relationships


Architecture knowledge is based on relationships.


Possible relationships:


### contains


Example:


System contains Components.



### depends_on


Example:


Quest System depends on Save System.



### affects


Example:


Configuration change affects Gameplay System.



### generated_by


Example:


Tool output generated by Engine.



### controlled_by


Example:


Feature controlled by Configuration.



Relationships allow Memory Core to understand impact beyond individual files.

## 7. Architecture Map and Analysis Layer


Analysis Layer may use Architecture Map to improve interpretation.


Without Architecture Map:



File changed


With Architecture Map:



File changed

↓

Component affected

↓

System affected

↓

Possible architectural area




Analysis provides suggestions.


Architecture Map provides approved context.



---

## 8. Architecture Map creation process


Architecture Map lifecycle:



DRAFT

↓

Human review

↓

APPROVED

↓

Used by Memory Core




DRAFT:

- proposed structure;
- incomplete knowledge;
- not trusted as final architecture.



APPROVED:

- reviewed;
- accepted;
- usable as project knowledge.



---

## 9. Architecture Map limitations


Architecture Map does not:


- automatically understand all project logic;
- replace source documentation;
- replace developers;
- modify project files;
- make architectural decisions.



It stores approved understanding.



---

## 10. Multi-project architecture knowledge


REQUIEM supports multiple projects.


Each project has independent architecture knowledge.


Example:



REQUIEM

Projects

Project A

Architecture Map

Project B

Architecture Map

Project C

Architecture Map



Shared knowledge may later contain:


- patterns;
- solutions;
- experience.



---

## 11. Current implementation state


Current:


- Architecture Map format exists as a DRAFT;
- Analysis Layer can read architecture information;
- no approved architecture map exists.



Not implemented:


- automatic architecture extraction;
- cross-project architecture knowledge;
- knowledge graph;
- engine-based architecture adapters.



---

## 12. Future direction


Architecture Map should evolve from:



Project description



into:



Project understanding model




The goal is not to know where files are located.


The goal is to understand what project systems exist, how they interact, and why they are designed this way.
